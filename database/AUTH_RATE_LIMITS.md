# Защита входа и регистрации

## Лимиты

| Ограничение | Значение |
| --- | --- |
| Общий бюджет POST login/register с источника, включая успешные запросы | 120 за 15 минут |
| Ошибки входа для пары источник + нормализованный email | 5 за 15 минут |
| Пауза по email независимо от источника | после третьей ошибки, 250 мс, 500 мс, 1 с, далее максимум 2 с |
| Одновременные попытки входа для одного email | 1, с аварийным сроком аренды 120 с |
| Попытки регистрации с источника | 10 за час |
| Попытки регистрации одного email со всех источников | 5 за час |
| Одновременные операции bcrypt в процессе | 2, без очереди |
| Операции bcrypt во всём развёртывании при общем хранилище | 4 |

Пауза на 15 минут касается только пары IP/email, поэтому ошибки одного клиента
не блокируют вход всем пользователям общей сети или владельцу из другой сети.
Email не получает длительной глобальной блокировки: общая пауза ограничена двумя
секундами. При направленной атаке возможны кратковременные ответы 429;
продолжительное удержание bcrypt/сбой процесса снимается по TTL аренды.
Счётчики имеют фиксированные окна и хранятся независимо от сессии/cookies.
Начало окна и отсчёт 15 минут — с первой попытки в этом окне.

Успешный вход обнуляет ошибки этой пары и общую задержку email, но не общий
бюджет источника и не ошибки других пар. При превышении возвращаются 429,
целочисленный `Retry-After` в секундах и сообщение о временном ограничении.
Все запросы регистрации, включая дубликаты и некорректные данные, расходуют бюджет.
Неверный пароль, неизвестный и заблокированный пользователь получают одинаковый
ответ 401. Для неизвестного адреса выполняется bcrypt.compare с фиктивным хешем
cost 12. Новые и существующие email при регистрации проходят хеширование cost 12
и получают один и тот же ответ 201. Существующий аккаунт и пароль не изменяются.
Различия планирования CPU/запросов БД не означают строгую гарантию constant-time.

Нормализация: trim и lowercase. Поиск дополнительно сравнивает LOWER(email)
побайтово, чтобы accent-insensitive collation MariaDB не позволяла входить под
вариантами адреса с другими диакритическими знаками и обходить ключи лимитера.
IP/email в хранилище представлены HMAC-SHA256 с ключом SESSION_SECRET.
Пароли, email, IP и токены сессий не записываются в таблицу или сообщения ошибок.

## Локальный запуск

По умолчанию `AUTH_RATE_STORE=memory`. Память ограничена 20 000 ключей;
при заполнении истёкшие записи удаляются, при нехватке места возвращается 429.
Счётчики не разделяются между процессами и сбрасываются после перезапуска.
Это режим для разработки. При NODE_ENV=production требуется mariadb-режим;
приложение откажется стартовать с memory-режимом.

## Production и несколько процессов

1. Сначала отдельно примените `database/migrations/006_auth_rate_limits.sql`
   к нужной базе под учётной записью миграций. Миграция создаёт только новую таблицу,
   повторный запуск допустим. Существующие users/listings не изменяются.
2. В окружении всех процессов задайте `AUTH_RATE_STORE=mariadb`,
   `NODE_ENV=production` и одинаковый криптографически случайный SESSION_SECRET
   длиной не менее 32 байт. Не помещайте значения секретов в команды/репозиторий.
3. Приложению нужны SELECT, INSERT, UPDATE для auth_rate_limits. Обслуживающей
   задаче также нужен DELETE. Используйте один primary MariaDB, без читающей реплики.
4. Запускайте `node scripts/prune-auth-rate-limits.js` по расписанию, например
   раз в минуту. Одна команда удаляет до 1000 истёкших записей. При большом объёме
   увеличьте частоту обслуживания. Команда изменяет только таблицу лимитов.
5. Проверьте HTTP 429, Retry-After и совместный бюджет на двух процессах.

Изменения счётчиков и аренды bcrypt выполняются в транзакциях с блокировками
строк. Время берётся у MariaDB. При недоступности хранилища запрос получает
503 и Retry-After: 5; автоматического перехода к независимой памяти нет.
При аварии процесса общий слот освобождается по TTL 120 с. Локальный лимит
работает дополнительно к общему. Пакеты Redis или другие новые зависимости
для этого варианта не требуются.

## Reverse proxy

По умолчанию `trust proxy=false`: X-Forwarded-For, Forwarded и X-Real-IP
не определяют источник лимитов. Прежнее безусловное доверие одному hop удалено.
Если приложение стоит за reverse proxy, в TRUSTED_PROXIES укажите через запятую
только его реальные адреса/CIDR, например `127.0.0.1/32,::1/128` для локального
прокси. Значения true, число hop и сети /0 не принимаются.

Прокси обязан перезаписывать недоверенные forwarded-заголовки; внешний доступ
к Node.js в обход прокси должен быть закрыт. Эта настройка также влияет на
распознавание HTTPS для Secure cookies express-session. Без неё за прокси
бюджет может оказаться общим для всех клиентов, а Secure cookie не установится.
При корректной настройке Express вычисляет req.ip по доверенной цепочке.

## Проверка

`node tests/auth-security.integration.js` использует только euromarket_test:
006 применяется повторно, тестовые аккаунты откатываются транзакцией, служебные
ключи теста удаляются адресно. Рабочая база и .env не изменяются. Проверяются
HTTP-сценарии, независимость источников/аккаунтов, подмена заголовков,
ограничения bcrypt и атомарное общее хранилище двух экземпляров.
